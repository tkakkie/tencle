# ADR 0006：User の作成手順、既存の User の招待の受諾、ユーザー単位の出来事の記録先

- 状態：採用
- 日付：2026-09-26
- 関連：Issue #6、スパイクのブランチ `spike-6-walking-skeleton`、[要件定義 §1.3・§5.1](../requirements.md#13-実装で確かめる項目)、I-4・I-31・I-34

## 背景

要件定義 §1.3 で、M1 の縦断の実装で決めることにしていた項目のうち、次をこの ADR で決める。

- テナント作成用ロールの権限（最初の admin の作り方を含む）
- 既に User を持つ人の、別テナントの招待の受諾
- パスワードの変更・再設定など、テナントに属さない出来事の監査先（I-4 との両立）

## 決定

### User を作る経路は2つだけ

1. **テナントの作成（CLI）**：テナント作成用ロールで、1つのトランザクションで Tenant・自寺の Temple・最初の admin の User と Membership・監査（System Actor）を作り、同じトランザクションでパスワード設定のメールのジョブを入れる（I-31）。標準の種別マスタは M2 で同じトランザクションに足す
   - メールアドレスの User が既にあれば再利用し、Membership だけを作る。この場合はパスワード設定のメールを送らない
   - 新しい User のパスワードは使えない値（乱数のパスワードのハッシュ。ADR 0004）にしておき、メールのトークン（`password_reset` の用途、72時間）で本人が設定する
   - 同じ slug で再実行すると一意制約で失敗し、何も変わらない。途中で失敗したら何も残らない（スパイクで、監査の書き込みを一時的なトリガーで失敗させて確かめた）
2. **招待の受諾**：例外関数（招待の受諾による User の作成）で作る

### テナント作成用ロールの権限

- 権限の範囲は[DB ロール](../architecture/invariants.md#dbロール)の表を正とし、同じ PR で具体的に書いた。既存の User の再利用のための `users` の `SELECT` と、ジョブの挿入のための `river_job` の権限を含む
- ID はアプリで作り、`RETURNING` に要る `SELECT` を広げない

### 既に User を持つ人の招待の受諾

- 招待のメールアドレスの User が既にある場合、**その User でログインしている**ときだけ受諾できる。受諾のユースケースが使う User は、セッションの照合の結果だけから決め、リクエストの値（ボディの ID など）を使わない（HTTP のテストは #10 で付ける）。ログインしていないか別の User なら「ログインしてから受諾してください」として拒否し、画面はログインの後に同じ受諾の URL に戻す
- 拒否したときはトランザクション全体を戻すので、トークンは消費されない（スパイクで確かめた）
- この応答は User の有無を表すが、**有効な招待トークンで宛先を確かめた後**にだけ返す。トークンは宛先のメールを受け取れた人だけが持つので、第三者がメールアドレスの登録の有無を調べる手段にはならない。招待の作成とパスワード再設定の要求の応答は、これまでどおり User の有無で変えない。I-34 にこの限定の例外を書く（同じ PR で不変条件を更新する）
- 受諾の監査の Actor は、作った Membership 自身とする（ADR 0005）
- メールアドレスは、入力の境界（ログイン・招待の作成・テナントの作成）で1つの関数で正規化してから保存・比較する。正規化は前後の空白の除去と小文字化とする。スパイクで、大文字を混ぜた招待・ログイン・テナントの作成で同じ User に行き着くことを確かめた

### パスワード設定のメールのジョブ

- 処理の時点で、User が既にパスワードを設定していれば送らない（遅れて実行・再試行されたジョブで、使っている人にパスワード設定のトークンを送らないため）。宛先の取得の例外関数が「設定済みかどうか」も返す（ハッシュは返さない）。スパイクで確かめた

### CLI の入口

- `tencle create-tenant` の配線（引数とテナント作成用ロールの接続）はスパイクで作っていない。テナント作成用ロールでの作成・重複・途中の失敗は `tenancy.Create` を直接呼んで確かめた。CLI は #8 で作り、その入口からのテストを付ける

### 途中の失敗

- 受諾は、トークンの消費・User の作成・招待の消費・Membership の作成・監査を1つのトランザクションで行う。スパイクで、新しい User を作った後の監査の書き込みを失敗させ、User も招待の消費もトークンの消費も残らず、同じトークンで再試行できることを確かめた
- パスワード再設定も同様に、`user_events` への記録を失敗させ、パスワードもセッションもトークンも元のままで、同じトークンで再試行できることを確かめた

### 招待のメールのジョブ

- ジョブの引数は、テナントの ID・依頼者の Membership の ID・招待の ID・引数の版だけとする（I-20）
- ワーカーはテナント文脈を設定し、処理の時点で、依頼者がまだ有効な admin か、招待が未受諾・期限内かを読み直す。だめなら送らない。宛先はテナント文脈のままアプリ用ロールで招待から読むので、例外関数は使わない
- スパイクで、依頼者の無効化・招待の取消・別テナントの指定のときに送らず、条件を満たせば送ることを確かめた

### ユーザー単位の出来事の記録先

- パスワードの変更・再設定など、どのテナントにも属さない出来事は、テナント所有の監査ログではなく、`user_events` 表に記録する
- `user_events` は User ごとの表で、RLS で本人の行だけが見え（`user_id = app.user_id`）、アプリ用ロールは `SELECT`・`INSERT` だけを持つ（追記のみ）。記録するのは出来事の種類と日時だけで、値（パスワードのハッシュなど）は記録しない（I-35）
- 業務データからは参照しない。テナント所有でない利用者単位の表として `User` を参照してよいことを I-4 に書く（同じ PR で不変条件を更新する）
- 本人しか読めないので、乗っ取りの調査（パスワードを変えられた後など）には使えない。調査が必要になったら、出来事の種類と日時だけを返す例外関数を保守用ロールに足す（アプリ用ロールに他の User の行を読ませない）
- パスワード再設定では、トークンの消費・パスワードの更新（全セッションの失効を含む）・`user_events` への記録を1つのトランザクションで行う

## 検討した代わりの案

- **最初の admin も招待で作る**：テナントの作成の直後に有効な admin がいない期間ができ、I-31 に反する
- **既存の User の受諾で、パスワードの入力で本人確認する**：ログインの画面と同じ確認を受諾の画面に作ることになる。ログインに一本化する方が、確認の経路が1つで済む
- **ユーザー単位の出来事を、所属する全テナントの監査ログに書く**：所属していないテナントが増えたときに記録が欠け、テナントの admin に別テナントでの出来事が見える
- **ユーザー単位の出来事を記録しない**：パスワードの変更は、乗っ取りの調査で最初に見る記録である

## 結果

- [テナント所有の範囲](../architecture/invariants.md#テナント所有の範囲)に `user_events` の行を加える（同じ PR で不変条件を更新する）
- 要件定義 §1.3 の M1 の項目は、この ADR と ADR 0003〜0005・0007 で決めたので、表から外す
- #8（テナントの作成）と #10（招待）でこの ADR に従って作る
