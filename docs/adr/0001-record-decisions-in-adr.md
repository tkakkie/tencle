# ADR 0001：設計判断を ADR で記録する

- 状態：採用
- 日付：2026-09-26

## 背景

1人とAIで長く保守するので、判断の理由が会話の中にしか残らないと、後から同じ議論を繰り返すことになる。

## 決定

後から変更すると影響の大きい設計判断は、`docs/adr/` にADRとして記録する。要件定義は方針と背景を、ADRは「ADRで決める」事項の詳細を、不変条件は常に守るルールを扱う。

## 検討した代わりの案

- Issue やPRの本文だけに残す：検索しにくく、どれが最新の決定か分からなくなる

## 結果

判断の理由を追える。ADRを書く手間がかかるので、後から変えにくいものだけに使う。
