# ADR 0002：Go で作り直し、AIのワークフローを軽くする

- 状態：採用
- 日付：2026-09-26

## 背景

Elixir・Ash Framework で設計していた旧版は、アプリのコードが0行のまま、プロセスの文書（約600行）と、GitHub の操作を守る自作のガード（hook とテストで約2,500行）が膨らんだ。Ash の前提に合わせて確かめる項目（読み取りのトランザクション、AshAuthentication の適合、bulk 処理）も多かった。人間はリポジトリを削除し、要件定義はそのままで作り直すと決めた。

前提は、バックエンドで50万行規模、10年保守である。

## 決定

**技術**

- 言語は Go とし、単一のバイナリのモジュラーモノリスにする。モジュールはトランザクションの境界で大きめに分ける（[要件定義 §3](../requirements.md#3-技術スタック)）
- 画面は templ + htmx、DBは pgx・sqlc、ジョブは River とする
- 認証は自作する

**プロセス**（[workflow.md](../process/workflow.md)）

- 人間はレビュー（GitHub での承認）だけを行い、それ以外はAIが自動で進める
- AIは bot アカウントで GitHub に書き込み、`main` へのマージには人間の承認を ruleset で必須にする。自作のガードは作らない
- AIが作ったものは別のベンダーのAIがレビューする。実装とレビューは Claude・Codex・agy（Gemini）・Grok で分担し、Copilot は自動レビューだけに使う
- 機械で分かることはCIに任せ、AIのレビューは5つの観点に絞る。レビューのループは2ラウンドまでとする

**不変条件**

- 技術に依存する文面（Ash の Policy・Resource・Oban・LiveView・boundary など）を Go の構造に置き換えた。守る内容は変えていない
- プロセスの行を新しいプロセスに合わせた。I-32（人間の確認）は GitHub の承認に、I-38（GitHubを操作するAI）は bot アカウントに書き換えた
- I-40（受け入れテストを実装より前に別のAIが書き、書き換えを検査する）を廃止した。1つの変更ごとに AI の往復とゲートが増える割に、レビューの観点「テストが実装の誤りで失敗するか」で代えられると判断した

## 検討した代わりの案

- Elixir のまま続ける：Ash の前提を確かめる作業が多く、進みが遅かった
- SPA と API：言語とビルドが2つになり、項目ごとの認可をAPIで漏れなく行う負担が増える。業務のCRMには templ + htmx の表現力で足りる
- モジュールを細かく分ける：業務操作が複数のモジュールのロックを共有するので、モジュール間の整合性を自作することになる
- 人間のアカウントと自作のガードを続ける：GitHub の標準機能（bot と承認の必須化）で同じことを守れる

## 結果

- Ash の前提を確かめる項目の多くが不要になる。RLS のためのトランザクションは `db.TenantTx` 1つで扱える
- 認証、状態機械、監査などを自作するので、そのぶんのコードとテストが増える
- 受け入れテストの書き換えを機械で検出する仕組みがなくなる。テストの弱体化が問題になったら、検査を足すか I-40 に相当する規則を戻す
- bot アカウントのトークンの扱いを誤ると、人間のアカウントでAIが操作できてしまう。`gh pr review` を拒否する設定で補う
