# ADR 0007：ジョブのエラーに個人情報を残さない

- 状態：採用
- 日付：2026-09-26
- 関連：Issue #6、スパイクのブランチ `spike-6-walking-skeleton`、[要件定義 §1.3](../requirements.md#13-実装で確かめる項目)、I-19・I-20

## 背景

River は、ジョブが返したエラーの文字列をジョブの行（`river_job.errors`）に保存する。メールの送信サービスや外部の API のエラーには、宛先のメールアドレスなどの個人情報が入り得る。River のテーブルは RLS の対象外で、個人情報を入れない決まりである（I-20）。§1.3 で、その防ぎ方とテストを M1 で決めることにしていた。

## 決定

- **ジョブのワーカーは、外部から受け取ったエラーをそのまま返さない。** 外部の呼び出し（メールの送信など）の境界で、パッケージが公開する固定のエラー値（例：`mail: 送信に失敗しました`）に変換してから River に返す
- 分類が必要なら、エラーの種類（一時的か恒久的か、HTTP の状態コードなど）を許可リストの属性として固定のエラー値に持たせる。外部のエラーの本文は持たせない
- ログにも外部のエラーの本文を出さない。出すのはジョブの種類と許可リストの属性だけ（I-19）
- **DB のエラー（pgx）も、そのまま返さない。** サーバーのメッセージ（例：`invalid input syntax for type integer: "<値>"`）にも、クライアント側の引数の変換の失敗（pgx は引数を `%#v` で埋め込む）にも値が入る。ワーカーの境界で、DB のエラーは SQLSTATE だけを残した固定のエラーに変換する
- テストは、偽の送信先に**宛先を含むエラー**を返させ、カナリア値が `river_job.errors` とログのどちらにも残らないことを確かめる。River は自分のロガーを持つので、テストのロガーを `river.Config.Logger` にも渡し、ワーカーのログと River 自身の失敗のログ（River v0.47 は「Job errored」と記録する）が実際に捕まっていることを確かめてから、カナリアがないことを見る。DB のサーバー側とクライアント側のエラーにもカナリアを通し、変換の後に残らないことを確かめる（スパイクの形を #10 で本番のテストにする）

## 検討した代わりの案

- **River のエラーの保存を無効にする、または保存の前に加工するフックを使う**：River の内部の動きに依存する。ワーカーの境界で変換すれば、River の版に依存しない
- **エラーをそのまま返し、River の表を定期的に消す**：残っている間は個人情報が RLS の外にある

## 結果

- 失敗の原因を調べるときに、外部のエラーの本文が手元に残らない。調べるには、送信サービスの管理画面など、外部の側の記録を見る
- スパイクで、宛先を含むエラーを返す偽の送信先で、`river_job.errors` に残るのが固定の文言だけであり、ログにも宛先が出ないことを確かめた
