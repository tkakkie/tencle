# ADR 0003：RLS の実現方式（TenantTx・例外関数・DBロール）

- 状態：採用
- 日付：2026-09-26
- 関連：Issue #6、スパイクのブランチ `spike-6-walking-skeleton`、[要件定義 §4.3](../requirements.md#43-rlsの実現方式adr対象)

## 背景

テナント分離の規則（I-1〜I-3・I-34、[テナント所有の範囲](../architecture/invariants.md#テナント所有の範囲)、[DBロール](../architecture/invariants.md#dbロール)、[例外関数](../architecture/invariants.md#例外関数)）は不変条件で決まっているが、実現方法は M1 の縦断の実装で確かめてから決めることにしていた（要件定義 §1.2）。

スパイク（マージしないブランチ）で、アプリ用ロールの接続のまま、テナントの作成・ログイン・招待の受諾・テナントのデータの読み書き・ジョブ・業務操作のロックを通し、`go test -race` のテストで確かめた。

## 決定

### テナント文脈

- 文脈は `app.tenant_id`・`app.user_id` の2つで、`set_config(..., true)`（`SET LOCAL` と同じ）でトランザクション単位にだけ設定する
- ポリシーは直接 `current_setting` を読まず、`app_tenant_id()`・`app_user_id()`（未設定なら `NULL` を返す SQL 関数）と比べる。未設定なら比較が偽になり、何も見えない
- Go 側は `internal/platform/db` の3つの関数だけで文脈を扱う
  - `TenantTx(ctx, pool, tenantID, userID, fn)`：テナント所有データへのクエリはこの中でだけ実行する
  - `UserTx(ctx, pool, userID, fn)`：テナントを確定する前（ログイン済み・テナントなしのルート）
  - `SetContext(ctx, tx, tenantID, userID)`：実行中のトランザクションの文脈を設定し直す。招待の受諾とパスワード再設定のように、例外関数で始めた処理を**同じトランザクションのまま**テナント文脈に切り替えるときにだけ使う。呼び出し元は認証モジュールに限り、自作の静的解析で検査する
- ポリシーは、テナント所有のテーブルでは `USING` と `WITH CHECK` の両方を `tenant_id = app_tenant_id()` にする。`users` は「自分か、現テナントの所属者」、`auth_tokens` は「自分のもの」だけを見せる

### DB ロールと作成手順

| ロール | 名前 | 作り方 |
|---|---|---|
| マイグレーション用 | `tencle_migrator` | LOGIN・BYPASSRLS。スキーマ `public` の所有者 |
| アプリ用 | `tencle_app` | LOGIN。所有者でなく BYPASSRLS なし |
| テナント作成用 | `tencle_tenant_creator` | LOGIN・BYPASSRLS |
| 例外関数の読み取り用・書き込み用 | `tencle_fn_reader`・`tencle_fn_writer` | NOLOGIN・BYPASSRLS |

- ロールはクラスタ単位なので、マイグレーションの外の**初期設定の SQL**（`db/bootstrap/`）で作る。スーパーユーザーが実行し、何度実行しても同じ結果になるように書く（`IF NOT EXISTS`）。同じ SQL で、スキーマ `public` の所有者をマイグレーション用ロールにする
- マイグレーション用ロールには、例外関数の所有ロールへの `SET` だけを許す（`GRANT ... WITH INHERIT FALSE, SET TRUE`）。所有者の付け替えに要るが、権限は継承させない
- パスワードは開発では架空の値を使い（I-21）、本番の値と初期設定の実行手順は M1b のデプロイで決める

### 例外関数

- 名前は `fn_` で始め、`LANGUAGE sql`・`SECURITY DEFINER`・`SET search_path = pg_catalog, public` とする
- 所有者は、読み取りだけなら `tencle_fn_reader`、書き込みを伴うなら `tencle_fn_writer` にする。所有ロールには、例外関数の表の「読む」「書く」列だけの権限を与える
- 該当がないとき、`OUT` 引数の関数は **`NULL` の行**を返す。呼び出し側は `WHERE <列> IS NOT NULL` で絞るか、ポインタで受ける
- マイグレーションの書き方で、スパイクで見つかった2つの落とし穴を避ける
  1. **権限（`REVOKE ... FROM PUBLIC`・`GRANT`）は、所有者を付け替える前に設定する。** 付け替えた後はマイグレーション用ロールが所有者でなくなり、`REVOKE`・`GRANT` が警告だけで効かない。スパイクでは、そのせいで `PUBLIC` が例外関数を実行できる状態になっていた
  2. **所有者を付け替えるには、新しい所有者がスキーマの `CREATE` 権限を持つ必要がある**（PostgreSQL の仕様）。付け替えの間だけ与えて、終わったら取り消す
- `PUBLIC` から実行権限を外すのは tencle の関数だけにする（`ALL FUNCTIONS IN SCHEMA` にすると River の関数まで外れる）

### ロックと権限

- 業務操作（I-44）で集約の根を `FOR UPDATE` でロックするには、そのテーブルの**どれかの列の `UPDATE` 権限**が要る（PostgreSQL の仕様）。集約の根のテーブルでは、アプリ用ロールに少なくとも1つの列の `UPDATE` を与える（`tenants` では、テナント設定で変える `name`）

### River

- River のテーブルは RLS の対象外で、個人情報を入れない（I-20）。River のマイグレーション（`rivermigrate`）を tencle のマイグレーション（goose）より先に、同じマイグレーション用ロールで適用する。River のテーブルへの権限を tencle のマイグレーションで与えるためである
- アプリ用ロールには River のテーブルの `SELECT`・`INSERT`・`UPDATE`・`DELETE` を与える
- テナント作成用ロールには、同じトランザクションでジョブを入れるために `river_job` の `SELECT`・`INSERT`・`UPDATE (kind)` を与える。River（v0.47）のジョブの挿入は `RETURNING` と `ON CONFLICT (unique_key) DO UPDATE SET kind` を使うためである。River を更新するときは、この前提が変わっていないかを確かめる

### ID と sqlc

- ID は UUID とし、Go 1.27 の標準ライブラリの `uuid` を使う（外部の依存を増やさない）。テナント作成用ロールのように `RETURNING` に要る `SELECT` 権限を持たせたくない場合は、ID をアプリで作る
- sqlc の生成コードは `New(tx)` で `TenantTx` のトランザクションに載せて使える。`uuid` 型は標準ライブラリの `uuid.UUID` に対応付ける（`overrides`）。`NULL` になり得る例外関数の戻り値は、ポインタか `NULL` を扱える型にする

### テスト

- テストごとに、スーパーユーザーの接続で使い捨てのデータベースを作り、初期設定とマイグレーションを適用し、以後は**アプリ用ロールの接続**で検証する。スーパーユーザーの接続は、検証のための読み取りと、失敗を起こすための一時的なトリガーにだけ使う。接続先は環境変数 `TENCLE_TEST_SUPERUSER_URL` で渡し、CI では PostgreSQL のサービスを使う
- 次の検証表をテストとして持つ（スパイクで作った形を #7 で本番のテストにする）

| 検証 | 確かめること |
|---|---|
| ロール | アプリ用ロールがスーパーユーザーでなく、BYPASSRLS がなく、テーブルを所有しない |
| RLS の有無 | 対象の各テーブルで RLS が有効かつ強制（`pg_class`） |
| 文脈なし | 文脈を設定しない接続では、どのテーブルも0行 |
| 自テナントだけ | 別テナントの行は読めず、書き込みは RLS の違反、更新は0行 |
| 文脈が漏れない | 接続を1本にしたプールで、コミット・ロールバックの後に文脈が残らない |
| `users`・`auth_tokens` | 自分と現テナントの所属者だけ、自分のトークンだけが見える |
| 秘密の列 | `hashed_password`・`token_hash` は権限なしで読めない |
| 例外関数 | 所有者・`SECURITY DEFINER`・`search_path`・`PUBLIC` が実行できないこと・アプリ用ロールが実行できること |
| テナントの作成 | アプリ用ロールでは作れない |

## 検討した代わりの案

- **接続単位で文脈を設定する**：プールで接続が使い回され、次の利用者に文脈が漏れる
- **ポリシーで `current_setting` を直接読む**：未設定のときにエラーになるか空文字になり、比較の扱いがテーブルごとにばらつく。関数にまとめる
- **例外関数を PL/pgSQL で書く**：今の例外関数は1文で書けるので、SQL 関数の方が短く、読み違いが少ない。複数の文が要るもの（パスワードの更新とセッションの失効）も SQL 関数で書けた
- **ロールをマイグレーションで作る**：ロールはクラスタ単位で、マイグレーション用ロールに `CREATEROLE` を持たせることになる
- **ロックに勧告的ロック（`pg_advisory_xact_lock`）を使う**：`UPDATE` 権限は要らないが、ロックの対象が行と結び付かず、I-44 の「集約の根の行をロックする」と読み比べにくい
- **UUID に外部のライブラリを使う**：Go 1.27 の標準ライブラリで足りる

## 結果

- スパイクのテストで、上の検証表はすべて通った。業務操作のテスト（2人の admin が同時に互いを降格する）は、Tenant のロックを外すと10回中10回失敗し、admin が0人になった。ロックがあれば毎回1人残る
- 初期設定の SQL がマイグレーションの外にあるので、ロールの変更はマイグレーションの履歴に残らない。ロールを変えるときは初期設定の SQL を更新し、本番での実行手順を M1b で決める
- goose のモジュールは、他のデータベースのドライバ（SQLite など）を自分のテストのために要求するので、`go.sum` が増える。バイナリには入らない（`go mod why` で goose のテストからだけ参照されることを確かめた）。依存の更新の負担が問題になったら、埋め込みの SQL を順に適用する小さな実装に置き換える
- #7（DB の基盤）で、この ADR に従って本番のコードとテストを作る
