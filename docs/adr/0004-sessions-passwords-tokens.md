# ADR 0004：セッションとパスワード、認証トークン

- 状態：採用
- 日付：2026-09-26
- 関連：Issue #6、スパイクのブランチ `spike-6-walking-skeleton`、[要件定義 §5](../requirements.md#5-認証認可)、I-8・I-10・I-34

## 背景

認証は自作する（要件定義 §5）。セッションとパスワードの方式、招待・パスワード再設定のトークンの発行方法は ADR で決めることにしていた（§1.2）。守るべき規則は、ハッシュだけを保存する（I-10）、無効化・権限の変更・パスワードの変更が即座に効く（I-8）、ユーザーの存在有無で応答を変えない（I-34）である。

## 決定

### パスワード

- argon2id（`golang.org/x/crypto/argon2`）で、PHC 形式の文字列（`$argon2id$v=19$m=...,t=...,p=...$<salt>$<hash>`）として `users.hashed_password` に保存する。引数は OWASP の推奨の最小値（メモリ 19 MiB、反復 2、並列 1、ソルト 16 バイト、鍵 32 バイト）から始める。文字列に引数を含めるので、後から強めても既存のハッシュを検証できる
- パスワードをまだ設定していない User（テナントの作成で作った最初の admin）の `hashed_password` は `!` にする。どのパスワードとも一致しない
- 存在しないメールアドレスでログインしたときも、固定のダミーのハッシュで検証して同じだけ時間をかけ、同じエラーを返す（I-34）

### 認証トークン

- セッション・招待・パスワード再設定を、1つの表 `auth_tokens` で扱う。用途は `kind`（`session`・`invitation`・`password_reset`）で区別する
- トークンは32バイトの乱数を base64url にしたもの。保存するのは SHA-256 のハッシュだけで、平文は発行時に一度だけ扱う（I-10）
- `subject_id` は用途の対象（招待なら招待のID、それ以外は User のID）、`user_id` は持ち主（招待では受諾まで User がないので `NULL`）
- 照合は、未消費・未失効・期限内のものだけを有効とする。消費は `UPDATE ... WHERE 未消費かつ期限内 ... RETURNING` の1文で行うので、同じトークンを並行に使っても1回だけ成立する（スパイクで8並行のテスト）
- 用途違いは照合で一致しないので拒否される（招待のトークンでパスワードは再設定できない）
- メールで送るトークンは、送信ジョブの中で発行してハッシュを保存する（I-10）。ジョブの引数は ID だけ

| 用途 | 期限 | 消費・失効 |
|---|---|---|
| セッション | 発行から7日（延長しない） | ログアウト、パスワードの変更・再設定で、その User の全セッションを失効 |
| 招待 | 招待の期限（作成から7日）と同じ。送信ジョブが招待の `expires_at` をトークンの期限にする | 受諾で消費。招待の取消で失効 |
| パスワード再設定 | 1時間 | 確定で消費 |
| 最初の admin のパスワード設定 | 72時間 | 確定で消費（用途は `password_reset` と同じ） |

### 認証の世代

- `users.credential_version`（認証の世代）を持ち、パスワードの更新で1つ上げる。セッションには、ログインで検証したときの世代を記録する
- セッションの照合は、トークンの世代が User の現在の世代と一致するときだけ有効とする
- 理由：ログインは「ハッシュを読む → 検証する → セッションを保存する」の順に進むので、その間にパスワードが更新されると、更新による全セッションの失効の**後に**、古いパスワードで検証したセッションが保存され得る。世代を比べれば、ロックなしでこの取り残しを防げる。スパイクで、照合の後に再設定を挟んでから古い世代でセッションを保存し、そのセッションが無効になることを確かめた

### セッション

- Cookie `tencle_session` にトークンを入れる。属性は `HttpOnly`・`Secure`・`SameSite=Lax`・`Path=/`、`Domain` は付けない。期限はトークンと同じ
- **毎回のリクエストで**、トークンを例外関数で照合して User を決め、テナントルートではそのテナントの有効な Membership と権限の段階を DB から読み直す。セッションに権限を持たせないので、無効化・権限の縮小は次のリクエストから効く（I-8）
- スパイクで確かめた範囲：サービスの関数で、同じセッションのまま降格・無効化が次の呼び出しで反映されること。HTTP（TLS の `httptest`）と Cookie を通して、ログインで上の属性の Cookie が付くこと、未ログインは 401、テナントルートの読み書き、ボディの `tenant_id` が作用しないこと、別テナントと存在しない slug が同じ 404 になること、無効化の後の次のリクエストが 404 になること
- パスワードの更新（例外関数）は、同じ関数の中で、その User の全セッションを失効させる。スパイクで、2つのセッションが再設定の後にどちらも使えなくなることを確かめた
- ログアウトは、例外関数の表のとおり、その User の全セッションを失効させる（端末ごとのログアウトは必要になってから考える）
- 変更のリクエストの CSRF 対策（AGENTS.md）は、#9 でセッションに結び付けたトークンとして作る。スパイクでは確かめていない

## 検討した代わりの案

- **署名付き Cookie にセッションの内容を持たせる（サーバーに状態を持たない）**：失効を即座に効かせるには結局サーバーで照合が要る（I-8）
- **トークンの用途ごとに表を分ける**：照合・消費・失効の例外関数が用途ごとに増える。用途の列で足りる
- **bcrypt**：要件定義 §5 で argon2id と決めている
- **セッションの期限を操作のたびに延長する**：毎回の書き込みが増える。業務の CRM で7日の固定で困るかは、使ってから判断する

## 結果

- 毎回のリクエストで、セッションの照合と Membership の読み直しの2回のクエリがかかる。問題になるまで最適化しない
- 最初の admin のパスワード設定に `password_reset` の用途を使うので、画面は再設定と共通にできる
- #9（認証）でこの ADR に従って作る。argon2id の引数は、本番の VPS で1回の検証にかかる時間を測ってから決め直す
