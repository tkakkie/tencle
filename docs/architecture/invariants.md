# 不変条件（Invariants）

常に成り立っていなければならないルール。各行には、そのルールを担保する仕組みを書く。仕組みはルールを書かれたとおりに証明するものでなければならず、弱いもので代用しない。機械的に検査できない部分は「レビュー」と書く。

「予定」は仕組みがまだ存在しないことを表す。設計段階で先に置いた行は「予定」とし、仕組みができるまではレビューで担保する。仕組みを作るIssueができたらその行にリンクする。

- 担保の仕組みの更新は、その仕組みを導入するPRで行う
- 行の削除と、行の文面を弱める変更にはADRが必要
- Elixir 版から Go 版への書き換え（技術に依存する文面の置き換えと、プロセスの行の整理）は [ADR 0002](../adr/0002-rebuild-in-go.md) に記録した
- 番号は再利用しない。そのため表の中で番号は順に並ばない

背景と理由は [要件定義](../requirements.md) を参照。本書は要件定義・ADRより優先する。**不変条件の中身を決める一覧（範囲、例外、許可項目、監査対象、業務操作など）は本書に置き、他の文書からは参照だけにする。**

用語は [用語集](../domain/glossary.md) に従う。

## テナント所有の範囲

I-1〜I-3 の対象となる「テナント所有」のテーブルの範囲。

| 分類 | 対象 | 守り方 |
|---|---|---|
| テナント所有 | 業務データ、テナント固有マスタ、Membership、監査ログ、招待、冪等性の記録、WebhookEndpoint、WebhookEvent、WebhookDelivery、Integration、IntegrationKey、案件番号のカウンタ | `tenant_id` とテナント文脈のRLS（I-1〜I-3） |
| テナントの根 | `tenants` | 自テナントの行だけが見えるRLS（I-2） |
| ユーザー | `users` | 自分と現テナントの所属者だけが見えるRLS（I-34） |
| 認証トークン | 認証トークンの表（`auth_tokens`） | 自分のトークンだけが見えるRLS。保存・照合・消費・失効は[例外関数](#例外関数)で行う |
| ユーザー単位の出来事 | `user_events` | 自分の行だけが見えるRLS。アプリ用ロールは追記のみ（[ADR 0006](../adr/0006-user-creation-and-invitation.md)） |
| システム共通マスタ | 宗派、都道府県、市区町村、郵便番号 | RLS対象外。アプリ用ロールは読み取りのみ（I-2） |
| ジョブ基盤 | `river_job` など River のテーブル | RLS対象外。個人情報を入れない（I-20） |

表にないテーブルを作るときは、本書にどの分類かを加える。`pg_class` を検査するテストは、この表を許可リストとして使う。

## DBロール

| ロール | ログイン | 用途 | 主な権限 |
|---|---|---|---|
| マイグレーション用ロール | 可（マイグレーション時のみ） | テーブルの所有者。マイグレーションとデータ移行 | 所有者、`BYPASSRLS` |
| アプリ用ロール | 可 | アプリの実行時とテスト | 非所有者、`BYPASSRLS` なし。秘密の列（`hashed_password` など）の `SELECT` なし |
| 例外関数の読み取り用所有ロール | 不可 | 読み取りだけの[例外関数](#例外関数)の所有者 | `BYPASSRLS`。表の「読む」列だけの `SELECT` |
| 例外関数の書き込み用所有ロール | 不可 | 書き込みを伴う[例外関数](#例外関数)の所有者 | `BYPASSRLS`。表の「読む」列の `SELECT` と、「書く」列だけの `INSERT` / `UPDATE` |
| テナント作成用ロール | 可（CLI・保守用コンテナのみ） | テナントの作成（I-31） | `BYPASSRLS`。`INSERT`：`tenants`・`temples`・`memberships`・監査ログ・標準の種別マスタ、`users` のID・メールアドレス・`hashed_password`。`SELECT`：`tenants` のID・slug（重複確認）、`users` のID・メールアドレス（既存Userの再利用）。ジョブの挿入のための `river_job` の `SELECT`・`INSERT`・`UPDATE (kind)` と、そのシーケンスの `USAGE`（River の挿入が `RETURNING` と `ON CONFLICT ... DO UPDATE` を使うため） |
| 保守用ロール | 可（CLI・保守用コンテナのみ） | 共通マスタの更新、Privacy Erasure | 共通マスタの書き込み、消去に必要な更新 |
| バックアップ用ロール | 可（バックアップ用コンテナのみ） | `pg_dump` | 読み取りのみ、`BYPASSRLS` |

- `BYPASSRLS` は表の権限の代わりにならない。各ロールには、上の表の権限を個別に与える
- アプリの実行環境には、アプリ用ロール以外の認証情報を置かない

## テナントと識別

| # | 不変条件 | 担保する仕組み |
|---|---|---|
| I-1 | テナント所有データへのすべての読み取り・更新・削除は現在のTenantでスコープされ、すべての作成は `tenant_id` を明示的に保存する。テナント所有データへのクエリは、テナント文脈を設定するトランザクション（`db.TenantTx`）の中でだけ実行し、すべて `tenant_id` で絞る。RLSの範囲の外（テナントの確定前のテナント所有データ、`users`・認証トークンのうち現在の文脈で見えないもの）を読み書きしてよいのは、[例外関数](#例外関数)の表にある処理だけで、表にある列だけを読み書きし、表にあるものだけを返す。例外関数は、読み取りだけなら読み取り用、書き込みを伴うなら書き込み用の所有ロールが所有し、`search_path` を固定し、`PUBLIC` から実行権限を外してアプリ用ロールにだけ与える。例外関数を呼ぶGoの包み関数は、表の「呼び出し元」だけが参照できる。RLSを迂回する汎用の手段は使わない。 | 予定：sqlc のクエリを走査し、テナント所有テーブルを参照するクエリに `tenant_id` の条件がないものを失敗させるテスト（許可リストあり）。他テナントから何も見えない結合テスト。各例外関数が表にない列を読み書き・返却しないテスト（所有ロールの権限で拒否されることを含む）。例外関数の表とDB関数の一覧が一致するテスト。各関数の所有者・`search_path`・実行権限を `pg_proc` で検査するテスト。Go の `internal` の規則と自作の静的解析で包み関数の呼び出し元を限定する |
| I-2 | [テナント所有の範囲](#テナント所有の範囲)でRLSの対象とした各テーブルは、RLS が有効かつ強制（`FORCE ROW LEVEL SECURITY`）されている。テナント文脈（`app.tenant_id`）とユーザー文脈（`app.user_id`）は `SET LOCAL` によりトランザクション単位でのみ設定し、RLSの対象のテーブル（テナント所有データ、`tenants`、`users`、認証トークン）へのクエリは読み取りを含めてすべてトランザクション内で実行する。各ロールは[DBロール](#dbロール)の表の権限だけを持つ。テストはアプリ用ロールで実行する。 | 予定：`pg_class` を検査し、対象の各テーブルで RLS が有効かつ強制されていることを確認するテスト。テナント未設定・別テナント設定では何も見えない結合テスト。プールから再利用された接続に設定が残らないテスト。各ロールの属性と権限を検査するテスト。テスト用接続がアプリ用ロールであることを起動時に検査 |
| I-3 | テナント所有テーブル間の参照は、`tenant_id` を含む複合外部キーとする。参照先には `(tenant_id, id)` など対応する一意制約を置く。 | 予定：`pg_constraint` を走査し、テナント所有テーブル間の外部キーがすべて `tenant_id` を含むことを確認するスキーマテスト |
| I-4 | 業務データは `User` を参照しない。「誰が」は Actor（Membership / Integration / System）で表す。テナント所有テーブルのうち `User` を参照するのは `Membership` のみ。 | 予定：`Membership` 以外のテナント所有テーブルに `user_id` 列や `User` への外部キーがないことを確認するスキーマテスト |
| I-5 | すべてのルートは、[ルートの種類](#ルートの種類と否定テスト)のいずれかとして1か所に種類付きで登録される。テナントルートではテナントをURLのslugから決め、ログインユーザーがそのTenantに有効なMembershipを持たなければ404を返す。存在しないslugとMembershipのないslugは同じ404にする。APIでは、テナントを検証したIntegrationから決め、クライアントの指定（URL・ヘッダー・ボディ）を使わない。テナントもテナント所有リソースのIDも、他テナントのものをリクエストで指定しても作用しない。開発専用ルートは本番のビルドに含まれない。 | 予定：ルート表を走査し、[種類ごとの否定テスト](#ルートの種類と否定テスト)を表駆動で網羅する。本番ビルドのルート一覧に開発専用ルートがないテスト。応答時間の差による判別は対象外とする |
| I-34 | `users` テーブルは、ログインユーザー自身の行（`app.user_id`）と、現在のテナントに所属するユーザーの行だけが見える。アプリ用ロールは `hashed_password` などの秘密の列を読めない。パスワードハッシュを返すのはログインの例外関数だけで、それを受け取れるのは認証モジュールだけである。Userの作成と照合は[例外関数](#例外関数)で行う。ただし、テナントの作成（CLI）では、テナント作成用ロールが同じトランザクションで最初のadminのUserを照合・作成する（I-31、[DBロール](#dbロール)）。招待の作成・パスワード再設定の要求の応答は、ユーザーの存在有無で変えない。ただし、有効な招待トークンで招待の宛先を確かめた後の受諾の画面では、宛先のメールアドレスのUserが既にあれば「ログインしてから受諾してください」と応答してよい（トークンは宛先のメールを受け取れた人だけが持つため。[ADR 0006](../adr/0006-user-creation-and-invitation.md)）。 | 予定：他テナントだけに所属するユーザーが見えない結合テスト。同じテナントの他のユーザーの秘密の列を読めないテスト。存在するメールと存在しないメールで、送信されるメール以外に外部から観測できる差がないテスト |
| I-31 | 各Tenantには有効な `admin` のMembershipが常に1人以上いる。テナントの作成は、CLIからテナント作成用ロールで、Tenant・自寺のTemple・最初のadminのUserとMembership・標準の種別マスタを1つのトランザクションで作る。最後のadminの無効化・降格は拒否する。 | 予定：テナント作成が上記を同一トランザクションで作り、途中で失敗すると何も残らないテスト。アプリ用ロールではテナントを作成できないテスト。最後のadminの無効化・降格が拒否されるテスト。2人のadminが同時に互いを降格・無効化しても、少なくとも1人が残る並行テスト |
| I-27 | 各Tenantには自寺（`kind = own`）のTempleがちょうど1つある。自寺の削除・アーカイブ・`kind` の変更はできない。 | 予定：`unique (tenant_id) where kind = 'own'`。テナント作成が自寺を作るテスト（I-31）。自寺の削除・アーカイブ・`kind` の変更と、2つ目の自寺の作成が拒否されるテスト |

### 例外関数

RLSの範囲の外（テナントの確定前、または `users`・認証トークンのように現在のテナント文脈で守れないもの）を読み書きしてよい処理の一覧。ここにない処理を追加するには、本書の変更が要る。関数名と引数の詳細はADRで決める。

| 処理 | 呼び出し元 | 読む | 書く | 返すもの |
|---|---|---|---|---|
| ログインの照合 | 認証ルート、アカウント設定（パスワード変更時の現在のパスワードの確認）。いずれも認証モジュールから | `users` のID・正規化したメールアドレス・`hashed_password`・認証の世代 | なし | UserのID・`hashed_password`・認証の世代（検証はアプリ側で行う） |
| パスワードの更新 | パスワード再設定、パスワード変更（認証モジュール） | `users` のID・認証の世代、トークン表の持ち主のUserのID・種類・失効状態（更新の条件と計算に使う） | `users` の `hashed_password` と認証の世代（`UPDATE`。世代は1つ上げる）。同じトランザクションでそのUserの全セッションを失効させる | なし |
| メールアドレスによるUserの照合 | パスワード再設定、招待の作成、招待の受諾 | `users` のID・正規化したメールアドレス | なし | UserのID（ない場合は「なし」。ルートの応答は存在有無で変えない） |
| 認証トークンの保存 | メール送信ジョブ、ログイン | なし | トークン表のトークンハッシュ・種類・対象ID・持ち主のUserのID・期限・認証の世代（セッションのみ）（`INSERT`） | なし |
| 認証トークンの照合（消費しない） | セッションの確認（毎回のリクエスト）、招待・パスワード再設定の画面表示 | トークン表のトークンハッシュ・種類・対象ID・持ち主のUserのID・期限・消費状態・失効状態・認証の世代、`users` の認証の世代（セッションは世代が一致するときだけ有効） | なし | 有効かどうか、種類・対象ID・持ち主のUserのID |
| 認証トークンの消費 | 招待の受諾・パスワード再設定の確定（最後のPOST） | トークン表のトークンハッシュ・種類・対象ID・期限・消費状態・失効状態 | トークン表の消費日時（`UPDATE ... WHERE 未消費かつ期限内 ... RETURNING`） | 種類と対象ID（1回だけ成立する） |
| Userの全セッションの失効 | パスワードの更新、ログアウト | トークン表の持ち主のUserのID・種類・失効状態（更新の条件に使う） | トークン表の、そのUserのセッションの失効日時（`UPDATE`） | なし |
| User IDからのメールアドレスの取得 | メール送信ジョブのみ | `users` のメールアドレス・`hashed_password`（設定済みかどうかの判定だけに使い、返さない） | なし | メールアドレスと、パスワードを設定済みかどうか |
| 招待の照合 | 招待受諾 | 招待のID・TenantのID・状態・期限・宛先のメールアドレス・権限の段階・指定したPriestのID | なし | 読んだ項目 |
| 招待の受諾によるUserの作成 | 招待受諾 | `users` の正規化したメールアドレス（重複確認） | `users` のID・メールアドレス・`hashed_password`・確認日時（`INSERT`） | 作成したUserのID |
| ログインユーザー自身のMembershipと所属テナントの一覧 | ログイン済み（テナントなし）のルート | `memberships` のID・権限の段階・有効状態・TenantのID（`user_id = app.user_id` のもの）、`tenants` のID・slug・名称 | なし | 読んだ項目 |
| URLのslugからのTenant解決 | テナントルート | `tenants` のID・slug | なし | TenantのID |
| APIキーの照合 | API | IntegrationKey のキーハッシュ・IntegrationのID・TenantのID・期限・失効状態、Integration の有効状態 | IntegrationKey の最終利用日時 | IntegrationのID・TenantのID |
| 打診トークンの照合（将来） | 打診ルート | TempleRequestのID・TenantのID・状態・期限 | なし | 読んだ項目 |
| テナントIDの列挙 | System Actor の定期処理のみ | `tenants` のID | なし | TenantのID |

招待の受諾（最後のPOST）では、1つのトランザクションで、トークンの消費・Userの作成（この表の関数）を行い、テナント文脈に切り替えて、招待の消費（未消費のものだけを更新）・Membershipの作成・Priestへの紐付けをアプリ用ロールで行う。どこかで失敗したら何も残らない。パスワード再設定も同様に、トークンの消費とパスワードの更新を1つのトランザクションで行う。既にUserを持つ人は、そのUserでログインしているときだけ受諾できる（[ADR 0006](../adr/0006-user-creation-and-invitation.md)）。受諾で書く監査のActorは、受諾で作ったMembershipとする（[ADR 0005](../adr/0005-actor-storage.md)）。

### ルートの種類と否定テスト

| ルートの種類 | 例 | 否定テスト |
|---|---|---|
| 公開 | Health Check | 業務データ・個人情報・バージョン等の内部情報を返さない |
| 認証 | ログイン、パスワード再設定、招待受諾 | 各ルートの要件どおり。トークンが無い・不正・期限切れ・使用済み・用途違いなら拒否。同じトークンを同時に使っても1回だけ成立する |
| ログイン済み（テナントなし） | テナント選択、アカウント設定 | 未ログインなら拒否。自分以外のUserの情報を返さない |
| テナント | `/t/{tenant_slug}/...`（htmx の部分更新と SSE を含む） | 未ログイン→拒否。Membershipなし・無効→404。存在しないslugも同じ404。ボディで別テナントやそのリソースのIDを指定→作用しない。`priest` 段階は I-7 の範囲外→404 |
| 打診（将来） | `/temple-requests/{token}` | トークンが無い・不正・期限切れ・無効化済みなら拒否。[許可項目](#テナント外に見せる項目)以外を返さない |
| API（M3） | `/api/v1/...` | APIキーが無い・不正・期限切れ・失効済み・Integration無効なら拒否。クライアントが別テナントを指定しても作用しない。別テナントのリソースは404。Integrationの権限にない操作・項目は拒否 |
| 開発専用 | メールボックス表示 | 本番のビルドに存在しない（ビルドタグで除く） |

## 認可と可視性

| # | 不変条件 | 担保する仕組み |
|---|---|---|
| I-6 | 認可の判断はすべてサーバー側（`internal/authz`）で行う。画面の表示制御は補助であり、サーバーが行わない認可判断を画面が行うことはない。権限の段階は `admin ⊃ office ⊃ priest` で、上位は下位の権限をすべて含む。Integrationの権限は、許可した操作・項目だけを認め、それ以外は拒否する。テナントのデータを扱うすべてのユースケースは、Actor を受け取って認可を通ってから処理する。認証前の処理（ログイン、招待の受諾、パスワード再設定）は認証モジュールのユースケースとし、Actor を持たず、[例外関数](#例外関数)の表の範囲だけを扱う。ただし招待の受諾は、有効な招待トークンの消費をもって認可とし、その招待の範囲（そのテナント、その権限の段階、指定したPriest）のテナント内の操作（招待の消費、Membershipの作成、Priestへの紐付け）だけを、テナント文脈を設定してアプリ用ロールで行う。そのときに監査に記録する Actor は、受諾で作った Membership とする（[ADR 0005](../adr/0005-actor-storage.md)）。認可を省く手段は作らない。System Actor に必要な権限は、用途ごとに限定した System Actor 用の規則で与える。 | 予定：ユースケースの一覧 × 権限の段階・Integrationの権限の表駆動テスト（一覧に載っていないユースケースがあれば失敗する）。認証モジュール以外で Actor を受け取らない公開のユースケースを検出する自作の静的解析。画面だけで制御していないか：レビュー |
| I-42 | 認可を決めるコード（権限の段階の比較、「自分の担当」の範囲、項目ごとの可視性、Integrationの権限の判定）は、`internal/authz/**` にだけ置く。各モジュールは `authz` の関数を呼んで判断を受け取る。 | 予定：`authz` 以外のパッケージで権限の段階（`AccessLevel`）の値を比較・分岐していたら失敗する自作の静的解析 |

### 業務操作

複数の行やエンティティにまたがる判断を伴う変更は、次の操作としてだけ行う（I-44）。操作名は目安で、識別子は実装時に用語集へ加える。

| 操作 | ロックの対象 | 内容と規則 |
|---|---|---|
| `create_matter` | 案件番号のカウンタ（テナント×年） | Matter・対象故人・案件関係者を作り、採番する。作成の時点で「故人1人以上、主はちょうど1人」を満たす |
| `cancel_matter` | Matter | Matterをキャンセルし、予定のCeremonyをすべてキャンセルして `cancelled_with_matter` を付ける。既にキャンセル済みなら何もしない |
| `restore_matter` | Matter | Matterのキャンセルを取り消す（admin・理由必須。例外修正）。`cancelled_with_matter` が付いたCeremonyを予定に戻し、印を外す。それ以外のCeremonyは変えない |
| `add_ceremony` | Matter | Ceremonyを追加する。キャンセル中のMatterには追加できない。獲得経路が紹介のMatterは、紹介元がなければ追加できない（仮登録の終わり） |
| `complete_ceremony` / `cancel_ceremony` | Matter | Ceremonyを完了・キャンセルする。キャンセル中のMatterでは行えない。完了では `completed_sect_id` を固定する（I-47） |
| `reopen_ceremony` | Matter | 完了・キャンセルしたCeremonyを予定に戻す（admin・理由必須。例外修正）。キャンセル中のMatterでは行えない（先に `restore_matter`）。予定に戻すと `completed_sect_id` を空にし、再び完了したときに固定し直す |
| `replace_primary_deceased` / 対象故人の追加・削除 | Matter | 操作の前後で「1人以上、主はちょうど1人」を保つ |
| 割り当ての確定・取消 | Matter | CeremonyAssignmentの状態を変える。キャンセル中のMatter、完了・キャンセルしたCeremonyでは行えない。確定では `temple_id` を固定する（I-47） |
| `change_access_level` / `deactivate_membership` | Tenant | 権限の段階の変更、Membershipの無効化。「有効なadminが1人以上」（I-31）と「有効な `priest` 段階はPriestに紐付く」（I-28）を保つ |
| Priestの紐付け・紐付け解除・アーカイブ | Tenant | I-28 を保つ |

並行テストで確かめる組み合わせと期待する結果：

| 組み合わせ | 期待する結果 |
|---|---|
| `cancel_matter` と `add_ceremony` | 先にロックを取った方が成立する。キャンセルが先なら追加は拒否、追加が先ならその Ceremony もキャンセルされる |
| `cancel_matter` と `complete_ceremony` | 先にロックを取った方が成立する。完了が先ならその Ceremony は完了のまま残り、キャンセルの対象にならない |
| `restore_matter` と `reopen_ceremony` | 先にロックを取った方が成立し、後の方は Matter の状態を読み直して規則どおりに成立または拒否される |
| `replace_primary_deceased` と対象故人の削除 | どちらの順でも「1人以上、主はちょうど1人」が保たれる。保てない方は拒否される |
| 2人のadminが互いを降格・無効化 | 先にロックを取った方が成立し、後の方は「有効なadminが1人以上」を保てなければ拒否される |
| `change_access_level`（`priest` へ）と Priestの紐付け解除 | 後の方は I-28 を保てなければ拒否される |

### 消去の単位

- **Family単位を基本とする。** Family とそれに属する Contact・Deceased・Matter・Activity・スナップショット・監査ログの値・WebhookEvent・冪等性の記録から、個人情報をまとめて消す
- **個人単位の依頼**では、構造化された項目（氏名・かな・連絡先・住所・スナップショットのうち出所がその人のもの）は自動で消す。自由記述（Activity本文・備考）は、その人が属するFamilyの候補を一覧にして人が確認し、消去する
- 自由記述から個人を自動で完全に識別することは前提にしない

### 過去の事実として固定する項目

| 項目 | 固定する時点 | 理由 |
|---|---|---|
| `CeremonyAssignment.temple_id`（出仕したときの所属寺院） | 割り当てを確定したとき | 僧侶の所属変更で、過去の提携寺院別の実績が変わらないようにする |
| `Ceremony.completed_sect_id`（執り行った宗派） | 儀式を完了したとき（予定に戻すと空にし、再び完了したときに固定し直す） | 故人・案件の宗派の修正で、過去の宗派別の実績が変わらないようにする |
| `Ceremony.location_snapshot`（実施場所） | 実施場所を設定・変更したとき | I-15 |

名前の誤字の訂正など、過去にさかのぼってよいものは固定しない（IDで参照し、表示は現在の名前を使う）。固定した項目のうち個人情報を含むものは、I-18 の出所のIDを持つ。

### 監査対象

Family、Contact、ContactDeceasedRelation、Deceased、Matter、MatterDeceased、MatterContact、Ceremony、CeremonyAssignment、Activity、Temple、Priest、ReferralSource、ReferralSourceOffice、ReferralSourceContact、Venue、MatterType、CeremonyType、Membership（作成・権限の段階の変更・無効化・Priestとの紐付け）、招待（発行・受諾・取消）、パスワードの変更・再設定（出来事のみ）、Tenantの設定、Integration、IntegrationKey（発行・失効。値は記録しない）、WebhookEndpoint
