# 開発ワークフロー

Issueがマージ済みのPRになるまでの流れと、誰が（人かAIか）何をするかを定める。**プロセス（役割、レビュー、停止条件、高リスクの範囲、CI、ruleset、監査）は本書を唯一の正とする。** 本書は高リスクの対象である。

## 原則

- **人間はレビューだけを行う。** GitHub でPRを承認するか、コメントで差し戻す。それ以外（Issueの作成、実装、レビュー、PRの作成）はAIが自動で進める
- **AIが作ったものは、別のベンダーのAIがレビューする。**
- **機械で分かることはCIに任せる。** AIのレビューは、機械では見られないものに集中する
- **問題が起きてからプロセスを足す。** 同じ種類の失敗を2回見たら、lint・テスト・AGENTS.md のどれかに落とす

## 役割

| Issueの種類 | 実装 | 必須のレビュー | 高リスクのときの追加 |
|---|---|---|---|
| 設計の重いもの | Claude | Codex | agy と Grok を交互に |
| 仕様が明確なもの | Codex | Claude | agy と Grok を交互に |
| 小さいもの | agy と Grok を交互に | もう一方（agy が実装したら Grok、Grok が実装したら agy） | Codex |

- **設計の重いもの**：[高リスク](#高リスク)のパスに触るもの、新しい業務操作やモジュールの境界を決めるもの
- **小さいもの**：振る舞いの変更が小さく、数ファイルで済むもの（文言、単純なバグ、小さな追加）
- **仕様が明確なもの**：上のどちらでもないもの（マスタのCRUD、一覧、画面、検索など）
- すべてのPRに、GitHub Copilot の自動レビューが付く（PR作成時の1回）。Copilot は実装に使わない
- **司令塔**は Claude Code のセッションで、振り分け、レビューの集約、PRの作成、GitHubへの書き込みを行う
- 使うモデルは固定する。agy は `gemini-3.8-flash-high`（agy は Claude のモデルも選べるため、指定を省かない）、Grok は `grok-4.7`
- 担当のAIが使えない（利用上限、障害）ときは、実装とレビューが別のベンダーであることを保って入れ替え、PRの集約コメントに記録する

## 流れ

```text
① 司令塔がマイルストーンからIssueを作る（目的、受け入れ条件、種類、高リスクかどうか）
② 種類に応じて実装の担当に振り分け、worktree で実行する
③ 実装の担当が make check を通す。司令塔が同じ検査をもう一度実行して確かめる
④ 別のベンダーがレビューし、指摘を JSON で返す
⑤ blocker の指摘があれば、実装の担当が直し、レビューの担当が前回のレビュー以降の差分とその影響範囲を確かめ直す（最大2ラウンド）
⑥ 司令塔が bot アカウントで push し、PRを作る → CI、Copilot、（高リスクなら）追加のレビュー
⑦ 司令塔が全レビューをPRの1つのコメントに集約する。未解決の blocker がなければ auto-merge を予約して人間に知らせ、あれば ⑤ に戻る
⑧ 人間が承認する、またはコメントで差し戻す（差し戻しなら ⑤ に戻る）
⑨ 承認とCIの成功がそろうと、自動でマージされる
```

- worktree はリポジトリの隣の `../wt/` に置く。複数のIssueを並行して進めてよい
- 計画の承認は求めない。高リスクのIssueは、実装の前に実装の担当が計画をIssueに書き、計画を書いたAIとは別のベンダーのAIが1回レビューする
- 高リスクの変更（認可・マイグレーション）と画面の変更は、別のPRに分けることを既定にする。人間が差分全体を読む範囲を小さくするためである

## レビュー

AIのレビューは、次の5点だけを見る。フォーマット、lint、型、テストの成否など、CIで分かることは指摘しない。

1. Issueの受け入れ条件を満たしているか。Issueの外を変えていないか
2. テストが、実装の誤りで本当に失敗するか（アサーションがない、必ず成功するテストを見つける）
3. トランザクション、ロックの順序、並行性（I-44）
4. 認可とテナントの境界（新しいユースケースが認可を通っているか、[不変条件](../architecture/invariants.md)を守っているか）
5. 設計（モジュールの境界、命名が用語集に合っているか、変更しやすさ）

指摘は、重大度（`blocker`・`major`・`minor`）、ファイルと行、要約、理由を持つJSONで返す。`blocker` は、見つかった時期（PRの作成前か後か、人間の差し戻しか）によらず、直して確かめ直すまで承認待ちに進めない。PRの作成後に見つかったら auto-merge の予約を外す。`major` は直すか、直さない理由を書く。`minor` は司令塔が判断する。

### 集約コメント

司令塔は、AIのレビューと Copilot の指摘をPRの1つのコメントにまとめ、更新し続ける。人間はこのコメントとCIの結果を読んで判断する。

- 冒頭の3行：判断してほしいこと、高リスクかどうか（読むべき範囲）、未解決の指摘の数
- 誰が実装し、誰がレビューしたか
- 指摘ごとに、出所、要約、対応（採用・不採用と理由）

## 停止条件

次の場合は、PRを draft のまま `needs-human` ラベルを付け、3行の要約とともに人間に知らせ、次のIssueに進む。

- Issueの範囲が広がる。Issueにない依存の追加が必要になる
- 抑制コメントの追加、チェッカー設定の緩和、既存のテストの削除や検証の緩和が必要になる
- マイグレーションが旧版と互換にできず、停止移行が必要になる（I-46）
- レビューのループが上限（2ラウンド）に達した
- レビューでセキュリティ上の指摘が出た。この場合、指摘の中身は公開の場に書かない（I-33）
- 担当のAIやツールが使えず、別のベンダーで代えられない

## 高リスク

次に当たるPRは高リスクとし、人間が差分全体を読む。それ以外のPRでは、人間は集約コメントとCIの結果を読み、差分は必要に応じて読む。

**パス**

- AIとGitHubの設定：`.github/**`、`.claude/**`、`AGENTS.md`、`CLAUDE.md`、`tools/ship/**`
- 検査：`.golangci.yml`、`tools/lint/**`、Makefile
- 依存・ビルド・デプロイ：`go.mod`、`go.sum`、`Dockerfile*`、`*compose*.yml`、`deploy/**`
- DB：`db/migrations/**`
- 認可・認証・テナント：`internal/authz/**`、`internal/identity/**`、`internal/tenancy/**`、`internal/platform/db/**`、`internal/erasure/**`
- CLI：`cmd/**`
- 文書：`docs/architecture/**`、`docs/process/**`、`docs/adr/**`、`docs/domain/**`、`docs/requirements.md`

**追加した行の内容**：`//nolint`、`set_config`、`SET ROLE`、`FOR UPDATE`、`SECURITY DEFINER`、`ROW LEVEL SECURITY`、`BYPASSRLS`

判定は、CIがパスと内容から行い、PRにラベル `risk:high` を付ける（予定。それまでは司令塔が本節で判定する）。

## CI

必須チェックは次のとおり。ruleset には、そのチェックを導入するPRがマージされてから加える（存在しないチェックを必須にすると、どのPRもマージできなくなるため）。

| 分類 | チェック |
|---|---|
| Go | フォーマット（gofmt）、`go vet`、ビルド（`go build`）、golangci-lint（自作の静的解析を含む）、`go test -race`（本物のPostgreSQL、アプリ用ロール） |
| 生成物 | sqlc・templ を生成し直して差分がないこと |
| DB | squawk（マイグレーション） |
| 依存 | govulncheck |
| リポジトリ | gitleaks、actionlint、zizmor、Docker Compose の構成（`docker compose config`） |

- PRのコードを実行するジョブは `permissions` を読み取りのみにし、`actions/checkout` は `persist-credentials: false` にし、secrets を使わない（I-39）
- 必須チェックのジョブには `if:` やパスの絞り込みを付けない（スキップが成功扱いになるため）

## ruleset

`main` の ruleset（I-25、I-32）は次のとおり設定済みである。

- PR必須、squash merge のみ、線形の履歴、force push と削除の禁止
- 承認1、最後の push の承認（最後に push した人以外の承認が必要）、push による古い承認の破棄、レビューのスレッドの解決
- Copilot の自動レビュー（PR作成時の1回。push のたびには行わない）
- バイパスできる人・アプリを置かない（管理者である人間のアカウントも含む）

リポジトリの設定：auto-merge を有効、マージ後のブランチ削除を有効、ワークフローの既定の権限は読み取りのみ、「Actions による PR の作成・承認」は無効、secret scanning と push protection と private vulnerability reporting を有効。

緊急時（必須チェックの故障でセキュリティ修正をマージできない等）は、人間が自分で、故障している必須チェックだけを一時的に ruleset から外す。PR必須・承認・最後の push の承認・バイパスなしは緩めない（I-25、I-32）。理由・外したチェック・元に戻したことをIssueに記録する。

## GitHubの認証情報とサンドボックス

- tencle のセッションは、bot アカウントのトークンで GitHub に書き込む。コミットしない `.claude/settings.local.json` の `env` に、bot のトークン（`GH_TOKEN`）と、tencle 専用の gh の設定ディレクトリ（`GH_CONFIG_DIR`）を置く。専用の設定ディレクトリには人間のアカウントを登録しないので、gh は人間の認証情報を見つけない
- 人間のアカウントでの承認と管理者の操作に当たるコマンド（`gh pr review`、`gh auth`、リポジトリの設定の変更と削除、ruleset の API）と、環境変数の差し替え・キーチェーンの読み出しは、設定で拒否する（`.claude/settings.json`）。API でのレビューの投稿のような別の形までは列挙しない（下の限界を参照）
- **限界**：同じ macOS ユーザーのキーチェーンには、別プロジェクトで使う人間のアカウントの認証情報が残る。上の対策は誤用を防ぐもので、AIが意図的にキーチェーンから取り出す迂回までは防げない。問題が起きたら、tencle のAIを別の macOS ユーザーかコンテナで動かす
- 実装とレビューの担当には GitHub の認証情報を渡さず、サンドボックスと worktree の中で動かす（I-38）。自動承認のフラグは、サンドボックスの中でだけ使う

## 定期監査

PRごとのレビューは差分しか見ないので、マイルストーンの区切りでコード全体を監査する。

- agy と Grok が交互に担当し、テナント分離と認可を中心に、`main` のコード全体を読む
- 再現するテストか `file:line` の根拠がない指摘は、優先度を下げる
- 指摘は1件につき1つのIssueにし、通常の流れで直す。セキュリティ上の指摘は公開の場に書かない（I-33）

## セキュリティ修正の手順

- 脆弱性の情報は、修正を公開するまで公開の場に書かない（I-33）
- 修正は Security Advisory の一時的な非公開フォークで行い、ローカルで `make check` を通し、人間が差分全体を読んで承認する
- マージ後に `main` のCIで確認し、Advisory を公開する

## 依存の更新

- Dependabot（Go modules、GitHub Actions、Docker）を使い、公開から一定期間たったものだけを提案させる（cooldown）。更新はグループにまとめ、週1回にする
- 司令塔が変更履歴の要約と注意点をPRにまとめる。`go.mod` の変更なので高リスクとして扱う
